# Orbis — Context for Claude Code

This is the Orbis project — a new Django 5.2 LTS application consolidating SEBPO's workforce-management systems. Built from scratch, UI modeled on the internal TimeLy product.

## Read this first, every session

**`docs/PLAN.md`** is the spec we're executing. Before making any substantive change, read it. It contains:

- Locked design decisions (Django 5.2 LTS, single `core/settings.py` + `python-dotenv`, email-as-username auth, app split, Tailwind via `django-tailwind`, etc.).
- Per-app responsibilities (`accounts`, `employees`, `roster`, `leave`, `attendance`, `dynamic_menu`, `theme`, `documents`, `offboarding`, `policies`, `payroll`).
- The dynamic-menu redesign (direct M2M on `MainMenu` / `SubMenu` — no intermediate `GroupMainMenu` / `GroupSubMenu` tables).
- The roster + leave unified-cell model (one `ShiftType` table; `LeavePolicy` OneToOne for leave-specific rules).
- The W1–W4 phased delivery plan targeting MVP on 2026-05-15.
- What NOT to port from the legacy ttms project.

## Current state

MVP target (2026-05-15) shipped on schedule, with several post-MVP items pulled forward. The codebase has 13 first-party apps:

- **`accounts`** — `CustomUser` (UUID pk, email-as-username, hierarchy via `JobInfo.reports_to` + `Department.head_of_department`), Microsoft Entra SSO with full JIT for `sebpo.com`, group-based + scope-based access control (`accounts/permissions.py`). Bulk new-joiner onboarding at `/users/bulk-create/` (**HR group only since 2026-10-05** — `accounts/views.py::HRRequiredMixin`, because the sheet and results workbook carry gross salary; `accounts/upload.py` + `upload_views.py`, same preview/apply/template shape as the `roster`/`payroll`/`employees` uploaders): one row per new hire creates `CustomUser` (+ optional `JobInfo`, + optional `SalaryStructure`), auto-assigning Employee ID (next numeric max) and a `first.last@sebpo.com`-style login Email when left blank — Data Solutions gets an initials convention instead, and collisions widen using more of the person's own name rather than a numeric suffix. The results workbook (Employee ID + Email + a generated one-time local password filled in) is what IT provisions the real Entra mailbox against, so `filter_users_by_claims`'s email match links first SSO login back to the pre-created row — meanwhile the local password (`ModelBackend`, always active alongside the OIDC backend) lets the new joiner sign in and fill in their own profile immediately, without waiting on Entra provisioning. The plaintext password exists only for that one apply request + results download; only its hash is ever persisted. `/users/create/` and the bulk uploader also capture **NID Number** (written to `employees.IdentificationNumber` with `id_type=NID` — not a `CustomUser` column, same single-source-of-truth precedent payroll uses for TIN) and **Notice Period (Months)** (`CustomUser.notice_period_months`, the contracted term agreed at hire). Every field on both flows is required except Team (bulk also keeps Employee ID/Email exempt, preserving auto-assign). Submitting an NID that already exists on file (any employee, active or not) surfaces a soft, non-blocking `messages.warning()`/report-table flag — `accounts/services.py::check_prior_employment` — showing the matched employee and, if they have an `ACCEPTED` `offboarding.Resignation`, its separation type/date; HR decides whether to proceed. No historical pre-Orbis NID data exists yet — the check only covers Orbis's own records so far. **Directory API** (phases 1–3 built 2026-10-14, `docs/DIRECTORY_API_PLAN.md`; consumer contract `docs/DIRECTORY_API.md`): Orbis is replacing Entra (still fed by the discontinued Oracle ERP) as the employee data source for other apps — SSO stays for authentication. Per-app `ApiClient` tokens (SHA-256 hash only, scopes `directory:read`/`roster:read`/`roster:write`, issued once from the admin's "Generate new token" action, superusers + User Admins) authenticate `/api/v1/directory/` (`accounts/api/`): reference lists, a paged employee list with an `updated_since` change feed, `employees/lookup/` (object id → email → employee id, 409 when keys name different people), detail, direct reports, and `employees/<id>/scope/` (Orbis's managed scope — downline ∪ department/team grants, each record tagged `via`/`depth`, sharing `accounts.permissions.reportee_depths` with the permission checks); all built over `accounts/api/views.py::employee_queryset` (constant queries per page). `CustomUser.entra_object_id` is recorded at every SSO login (never overwritten, never moved off another user) and matched before email. `CustomUser.directory_updated_at` is the change feed: `save()` bumps it only when a `CustomUser.DIRECTORY_FIELDS` value changes (not `auto_now` — logins would move it), so **a queryset `update()`/`bulk_update()` that writes a directory field must add `**directory_stamp(...)`**. The roster API (`roster/api/`) accepts `ApiClient` tokens by scope too (`HasApiScopeOrEnvToken`; `roster/?start_date=&end_date=` is the all-employee range mode), alongside `TIMELY_API_TOKEN`/`EXTERNAL_API_TOKEN` until TimeLy and dsndd switch over (plan §13); `manage.py import_entra_object_ids` backfills object ids from IT's Entra export. Developer docs live in Orbis at `/developers/api/` (`accounts/api/guide.py`), rendered from `docs/ORBIS_API_GUIDE.md`, `DIRECTORY_API.md` and `TIMELY_API.md` — edit the Markdown, not a template.

- **`leave`** — Full SEBPO Leave Policy v2.0: sandwich-leave rule, per-employee balance ledger with append-only transactions, carry-forward, encashment workflow, shift-summary report. The balance ledger debits from both approved `LeaveApplication`s and roster-direct `Shift` rows (most real leave never goes through the application form) — **instantly** via `leave/signals.py::sync_shift_leave_ledger` on every `Shift` save (same synchronous pattern as this app's CpL-grant signal), with `manage.py reconcile_shift_leave_usage` (nightly) only a catch-up for rows written via `bulk_create` (bypasses signals; bulk roster uploads do this on purpose). Idempotent via `LeaveBalanceTransaction.shift`, and reversed automatically if a reconciled Shift is later edited or deleted. **AL is anniversary-cycle, revised 2026-09-01** (supersedes the signed v2.0 PDF's 50%-carry-forward/quarterly-encashment clauses — a manager confirmation is the version implemented): cycle keys off each employee's own `joining_date` (`LeaveBalance.cycle_start`/`cycle_end`, closed nightly per-employee by `close_al_cycles.py`, not the old once-a-year calendar batch), 100% of unused AL carries forward with no per-cycle cut, capped at a 60-day lifetime running total (one-way freeze at cap, unchanged), no ongoing encashment. **AL's `accrued` is computed live** (`leave/services.py::live_accrued_al` — worked days ÷ 18 since cycle start, read fresh on every balance check), not from a monthly batch — `apply_monthly_accrual.py` no longer processes AL (dormant, kept for a hypothetical future non-anniversary policy) and is frozen into a permanent number exactly once, at `close_al_cycles.py`'s close time. Historical long-tenured employees' pre-Orbis balance is seeded once via `leave/upload_bank.py` into `LeaveBalance.opening`; separation payout stays a manual HR step (payroll settlement is Phase 5+, not built). **Shift-summary report (`payroll/reports.py::build_shift_summary`): the AL column, like every leave column, counts AL taken inside the report's start/end window; the AL *balance* is shown on the employee's own open anniversary cycle in separate "AL allocated / used / balance (cycle)" columns** via `_al_ledger_snapshot` (`live_accrued_al` + `live_used`) — revised 2026-10-30, reversing the 2026-09-02 cycle-based AL column; CL/SL stay window/calendar-year based. **A PENDING application is editable** (`/leave/<pk>/edit/`, `LeaveEditView`, 2026-10-19) on the same page as apply, by whoever could file it (`accounts.permissions::can_edit_leave` → `can_apply_leave_for`) — a plain row save, since nothing touches the ledger, roster or sandwich billing until approval; closed states 403 (cancel and re-apply). `leave/services.py::get_or_create_balance` self-heals a legacy-row `(employee, policy, year)` collision (a pre-2026-09-01 calendar-batch AL row silently masquerading as the current cycle, `cycle_start`/`cycle_end` NULL forever) the moment any caller touches an affected employee — found & fixed 2026-09-02 auditing a real employee, ~55% of AL balance rows company-wide had this. See `docs/LEAVE_POLICY_IMPLEMENTATION.md` §5.7 and "Risks worth calling out" for the full history, including the earlier accrual-doubling bug that surfaced (and was fixed) while first testing live accrual. **The Pending approvals and All leaves tabs default to "Direct reports only" (2026-10-10)** — a checkbox in the tab row (not the Filters popover: a scope switch, not a filter, so it never marks the popover active and must be visible on load), narrowing `pending_qs`/`all_qs` to `direct_report_pks` within the visible scope, the same default the roster grid uses; `?direct=0` widens to the full approval scope and rides through `_leave_filter_suffix`. A viewer with no direct reports (HR, typically) gets no checkbox and the full scope — unlike the roster grid's empty default for HR. `/attendance/corrections/`, `/roster/change-requests/` and the dedicated-night-shift list got the same switch 2026-10-16 (night shift's version reaches past below-Manager-tier managers to the nearest one who can approve, `core.approvals.night_shift_inbox_pks`), and the same rule scopes the **topbar notification bell** (all four types) (`core/approvals.py`, derived "waiting on you" — no stored notifications; v1 real-time is htmx polling + `orbis:approvals-changed` + a localStorage cross-tab nudge, WebSockets are v2; `docs/PLAN.md` "Notifications").
- **`attendance`** — TimeLy office-presence overlay, shipped post-MVP 2026-09-07. Labeled **"Timesheet"** everywhere user-facing (sidebar, page titles, Django admin app list via `AttendanceConfig.verbose_name`) since 2026-09-07 — the app name, models, and URL names all keep `attendance`/`Attendance*`, this is a display-only rename. `attendance/timely.py::fetch_office_presence` (60s-cached, never raises) still backs the dashboard's `working` bucket live for **today only**. Local history now lives in `AttendancePunch` (employee+date unique — deliberately not FK'd to `roster.Shift`, since a punch can exist for a date with no concrete Shift row and is an observed fact, not a scheduling record; joined to Shift/Roster at query time by `(employee_id, date)`), populated nightly by `manage.py sync_attendance_punches` at **10:00 Asia/Dhaka for the previous day** (not overnight — TimeLy's punch data isn't settled until ~7:00 AM the next morning), skipping TimeLy's unmapped `employee_id` rows. `time_in_office` is a `DurationField`, computed by the sync command itself as `check_out - check_in` (TimeLy's own dashboard does the same subtraction — its dev confirmed there's no finer-grained punch data behind it — so replicating it loses nothing; reverses the original "wait for TimeLy to report it directly" design, see `docs/PLAN.md`). `/attendance/` lists any synced date (`?date=`, defaults to yesterday) with the same `accounts.filters` q/department/team bar as `/employees/`; nav is a section header ("Timesheet") with two submenus — `Timesheet` (this list, open to `All Employees`, row-scoped by `visible_employees`, no `ProtectedView` gate) and `Corrections` below. The dashboard's `working` bucket page links out to it. Each row also shows the resolved **Shift** for that date (Shift row wins, else the weekly Roster pattern — same order as `today_status_buckets`; renders the `ShiftAttribute` name when set, e.g. `EVE 2-11`, else the `ShiftType` name), and a gold `⚠ Unaccounted` badge (`badge-warning`) when the resolved shift is WORK-category but there's no punch at all that date — not office-only, since TimeLy folds WFH in as remote punches; resolved per employee, so 24/7 teams working a weekend/holiday are still checked while teammates' regular off days aren't flagged. `?flagged=1` filters the whole scoped employee set (not just the page) with a live count badge, doubling as a company-wide daily reconciliation check. **Three modes off one URL** (`attendance/views.py::AttendanceListView`, `docs/PLAN.md` "Three modes"): single-employee date range (`?q=` is an exact employee ID or email, one row per date, cap 186 days; the bare URL defaults to the viewer's own month-to-date), **department/team date range** (added 2026-10-01 — `from != to` with a department or team effectively selected, one row per employee per date ordered employee-then-date, cap `TEAM_MAX_RANGE_DAYS = 31`; refused on "All departments" **except for `can_see_all` viewers** (HR/Admins/superusers, 2026-11-02), whose range is the payroll population for the span — leavers in, no-employee-ID accounts out — and pages over `(employee, date)` keys, building full rows for the page only (`_unaccounted_keys` + `_resolve_matrix`)), and the historic team mode (one date, one row per employee). Both range modes and every export go through `_build_timesheet_rows` over `_resolve_shifts_matrix` — constant query count. **`?export=xlsx`** ("Export Excel" button, any mode) downloads the full filtered row set via `attendance/exports.py::build_timesheet_export`, columns mirroring the table. **A team pick implies its department everywhere**: `accounts.filters.effective_filter_ids` backfills a hand-typed `?team=` with the team's own department (the filter bar's cascade never allows team-without-department in the UI), used by every `accounts.filters` consumer and the leave/attendance-corrections lists; `roster` keeps its own helpers. **Corrections** (`AttendanceCorrection`, `attendance/forms.py`, shipped 2026-09-07): a "Request correction" (or, for a date with no punch at all, "Add timesheet" — same button, same model/flow, label picked by whether `emp.punch` exists) action per row, plus a header-level "Add timesheet" button/"Timesheet pending" badge for the viewer's own row regardless of what the table's filtered to. All of them open the same right-hand drawer (`AttendanceCorrectionRequestView`, `?for=<pk>&date=`, `accounts.permissions::can_request_attendance_correction` — same `?for=` on-behalf-of shape as `leave.LeaveApplyView`; htmx GET → `_correction_request_drawer.html` fragment, non-htmx GET → a full-page fallback for direct navigation, same drawer-or-page split `policies` uses) proposing new check-in/out times, an *optional* `requested_time_in_office` (HH:MM:SS) override, and a reason. A successful POST returns `204 + HX-Redirect` back to `/attendance/` (htmx) or a normal redirect, so pending badges refresh; an invalid one re-renders the same fragment with `status=400`. The override exists because check-in/check-out is only ever the first and last punch of the day — an employee who punched in at 07:00, left the building for a few hours, and punched out at 23:00 has a 16h span but maybe a 9h actual office day, and TimeLy has no record of the gap; leaving it blank falls back to the plain `check_out - check_in` (`AttendanceCorrection.effective_time_in_office`), and both the form and model reject an override longer than the check-in/check-out span. The employee's manager (`JobInfo.reports_to`) or HR/Admins approve/decline at `/attendance/corrections/` (`can_act_on_attendance_correction` — same `_in_managed_scope` rule as `can_act_on_leave`, nobody approves their own). Approval writes straight onto `AttendancePunch` with `source=MANUAL_CORRECTION`, creating the row if none existed; `sync_attendance_punches` leaves a `MANUAL_CORRECTION` row's timestamps alone on any later resync for that date. **Editable while PENDING** (`AttendanceCorrectionEditView`, shipped 2026-09-07): the pencil icon next to a "Correction pending" badge (on `/attendance/` and the "My requests" tab of `/attendance/corrections/`) opens a right-hand drawer (`partials/_drawer_shell.html`, same Alpine `open()`/`close()` scaffold as `leave/list.html`'s balance drawer) rebinding the same `AttendanceCorrectionForm` to the existing instance — same permission as filing one (`can_request_attendance_correction`), and 403s the moment it's no longer PENDING. Saves in place (status/employee/date/punch untouched); an htmx POST closes the drawer via a bare 204 + `HX-Trigger: orbis:drawer-close` rather than swapping content, since the list row itself doesn't change until the request is actually approved. **Bulk approve/decline** (shipped 2026-09-07): a checkbox on every row a viewer could individually Approve/Decline, a header "select all" checkbox, and an Alpine-`x-show` toolbar ("Approve selected"/"Decline selected", hidden until ≥1 is checked) posting to `AttendanceCorrectionBulkActionView`. The checkboxes/buttons live outside the actual `<form>` (linked to it via the HTML5 `form="bulk-corrections-form"` attribute) since the table's per-row single-action `<form>`s can't be nested inside a wrapping one. Every id is still individually re-checked server-side; anything that fails (already handled, not yours, doesn't exist) is silently skipped rather than aborting the batch, and the result message counts both (`skipped = len(ids) - acted`). `_approve_correction`/`_decline_correction` are shared module-level functions — the single-row and bulk views both call them, so they can't drift apart.

- **`offboarding`** — `Resignation` (entry point — employee-submitted OR HR-on-behalf via `/offboarding/create/`) → 8-step clearance workflow (manager ack → HR → IT → Finance → asset return → exit interview → ERP → HR final). Structured `ExitInterview` + `AssetReturn` models. Auto-issues letters via `documents` when HR final step completes. LWD-driven deactivation via `LastWorkingDateMiddleware` (fast path, on request) + the nightly `deactivate_past_lwd` celery-beat job (backstop, 00:15). Deactivation is `last_working_date < today` — strictly past, so an employee keeps access through their LWD itself and drops off the next morning. `Resignation.notice_period_days` defaults from the resigning employee's own `CustomUser.notice_period_months` (× 30) when they self-submit, instead of the flat 30-day model default — HR can still override it. `Resignation.fell_short_of_notice`/`notice_shortfall_days` (computed `@property`s, not persisted — the underlying dates/notice_period_days stay editable up to ACCEPT) flag when actual notice given (`last_working_date − notice_start_date`) came in under that requirement; shown as a non-blocking `badge-warning` on the clearance queue and case detail page. Never write a crontab line, and don't describe these as cron in docstrings — beat is the only scheduler, and a second one double-runs the batch.
  - **`CELERY_BEAT_SCHEDULE` in `core/settings.py` MUST stay `{}`.** `DatabaseScheduler.setup_schedule()` pushes every entry there through `PeriodicTask.update_or_create()` on each beat startup, so a single entry silently reverts that task's admin-edited schedule/args/`enabled` on the next deploy (`update_orbis.sh` restarts beat every time). `scheduler/tests.py::BeatScheduleSourceOfTruthTests` fails if it's ever repopulated.
  - `seed_beat_schedule` is **get-or-create only** — it never overwrites an existing row, which is what makes it safe to run on every deploy. `--force` opts into a reset; `--only <name>` narrows it.
  - **Did it run?** Check `/admin/scheduler/scheduledtaskrun/` — `scheduler/monitoring.py` logs every beat-dispatched run (status, duration, captured command output) off the `periodic_task_name` header beat injects. Tasks dispatched via `defer()` carry no header and are deliberately not logged. The prod logs (`logs/celery.err.log` for the worker, `logs/celery_beat.err.log` for the scheduler's dispatch lines) are now the second stop, not the first.
  - Beat picks up an admin edit within ~5s, so pausing or retiming a job needs **no deploy and no restart**. The admin's "Run selected tasks" action dispatches an ad-hoc run without SSH, and **"Run once with arguments…"** (2026-10-30) does the same with extra arguments for that one dispatch — e.g. `--from 2026-10-21 --to 2026-10-22` on `sync_attendance_punches` after a TimeLy outage. Never add a `--date` to a row's saved `args` to resync: it pins the nightly to that date.
- **New table with a `CustomUser` FK = the migration needs the collation CONVERT step.** `CustomUser`'s pk is a UUID, which MySQL stores as `char(32)` — a *string*, so it carries a collation, and MySQL refuses a FK whose collations differ (`OperationalError 3780`). `CREATE TABLE` inherits the *database* default, not the collation of the table it references. Copy `_match_existing_collation` from `employees/migrations/0008_designationhistory.py` (an `ALTER TABLE <new_table> CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci` in a `RunPython`, placed last) **and set `atomic = False`** on the Migration — the step issues DDL, which Django forbids inside an atomic migration's transaction; FK creation is deferred to schema-editor exit, so convert-then-FK still orders correctly. `attendance/0002`, `leave/0010_cpl_grant.py`, `policies/0001` and `payroll/0002` all follow this. A `bigint` FK (Department, Team, …) is never affected. **Mirroring an existing model is not enough — mirror its migration too**; that omission cost a debugging detour on 2026-09-19. Full detail in `deploy/README.md`'s "MySQL collation" section.
- **Env vars**: read via `os.getenv()` with sensible defaults; never hardcode secrets. Both `manage.py` and `settings.py` load `.env` via `python-dotenv`. `PAYROLL_FIELD_KEYS` is required (settings refuse to load without it, like `SECRET_KEY`) — `.env.example` ships a throwaway dev key; `core/settings_test.py` pins its own.
- **Money display — whole taka, thousands grouping, everywhere.** Never render a Decimal raw or with `floatformat`: use `{{ x|taka }}` in templates (a template builtin, so it also works inside the DB-stored PDF designs — `core/templatetags/money.py`), `core.exports.money_value` + `set_money_columns` in Excel builders (cells stay numeric with `#,##0`), `core.money.format_taka` in Python, `core.admin_mixins.money_display` in admin `list_display`. **Inputs too (Finance, 2026-10-07): a money form field is `core.forms.TakaField`** — renders the value as an integer with `step="1"`, rounds a typed decimal half-up instead of rejecting it; `core.fields.EncryptedDecimalField.formfield()` returns it automatically, so every ModelForm/admin form over an encrypted money column already complies and only hand-built `forms.Form` money inputs need to name it. Finance's decision 2026-10-05: computed run figures are rounded at display time too, accepting a one-taka drift between a column and its printed total. `core/tests_money.py` scans every template and fails on a money attribute without `|taka`. Spec: `docs/MONEY_FORMAT_PLAN.md`.
- **Media files: never `.path`, never a raw `/media/` URL to nginx.** Read a `FileField` with `.open("rb")` (the Google Drive backend has no filesystem path) and link to it with `.url` (which is the permission-checked `media_serve` view on both backends). A new `upload_to` prefix needs a rule in `media_store/rules.py` or it 404s for everyone — that is the safe default. See the `media_store` bullet above.
- **A money column is a `core.fields.Encrypted*Field`, never a bare `DecimalField`.** `core/tests_encryption.py::RegistryGuardTests` fails on any plaintext `DecimalField` in `payroll` that isn't on its rate-card allow-list, and on any `order_by()`/`Sum()`/`Avg()`/`F()` naming an encrypted column. `isnull` is the only lookup; `values_list()`/`only()`/`update()` work normally.
- **Subagent model selection — reach for an Opus subagent on complex work.** When delegating via the `Agent` tool to something requiring deep reasoning (a hard multi-file bug, payroll/leave-ledger logic, architectural/data-model design, anything touching the AL live-accrual or shift-leave-ledger sync machinery), pass `model: "opus"` rather than inheriting the parent session's default. Routine delegation (search/`Explore`, straightforward CRUD, following an existing pattern like `StyledMixin` or `accounts.filters`) doesn't need the override — leave it unset. This doesn't change the primary session's own model, which is a user choice via `/model`.
- **OpenProject tracking (op.sebpo.net/projects/orbis)**: work packages are generated from `tools/openproject/inventory.yaml`. Every non-merge commit belongs to exactly one entry (`sync.py --check-commits`), so a commit that ships or extends a feature should add its hash to that entry in the same change. Never rename or reuse a `key`. Writing to OpenProject is outward-facing: dry-run first, and only `--apply` when the user asks. See `docs/OPENPROJECT.md`.
- **Plan drift check**: if you catch yourself adding a new library, a new app, or a new major pattern that's not in `docs/PLAN.md`, stop and update the plan first.
- **Form widget styling — use `form-input` on every widget, including `<select>`.** The theme defines `.form-input` (bg, border, padding, focus ring) plus a critical dark-mode rule `.dark select.form-input option { background-color: #0B333F; color: #fff }` that fixes the native dropdown options (which the OS renders with light backgrounds in dark mode otherwise). **Do NOT use `form-select`** — that class isn't defined anywhere; selects with it inherit broken native styling and unreadable dropdown options.
  - **For ModelForms, prefer `core.forms.StyledMixin`** (`employees/forms.py::_Base` is the reference). It auto-applies `form-input` to every widget except checkboxes (which use a different visual). For dynamic fields added in `__init__`, call `self.style_widgets()` AFTER adding them.
  - **For ad-hoc widget overrides** (not using StyledMixin), use `attrs={"class": "form-input"}` explicitly on `forms.Select`, `TextInput`, `Textarea`, `DateInput`, `NumberInput`. Use `attrs={"class": "form-checkbox"}` for `CheckboxInput`.
- **Dates — Flatpickr is the only date picker. Never `<input type="date">` or `type="datetime-local"`.** A native input renders the browser's own control, so the same form looks different per-OS and clashes with the Timely dark theme. Flatpickr is vendored (`static/vendor/flatpickr-4.6.13.*`) and `base.html::wireFlatpickr` binds every `[data-flatpickr]` (date) and `[data-flatpickr-datetime]` (date+time, `enableTime`) input on load **and after each htmx swap**, so drawer/OOB content works with no extra JS. ISO `Y-m-d` in, ISO out.
  - **In Python forms**, use `core.forms.use_date_picker(form, *field_names)` in `__init__` (it swaps the widget *and* pins `input_formats`, and skips names the form doesn't have — one call covers a create/edit pair). For a `Meta.widgets` dict or a field built inline, use `core.forms.date_widget("form-input")` / `datetime_widget("form-input")`; drop the `"form-input"` argument when the form runs `StyledMixin.style_widgets()`, which adds the class itself.
  - **In templates**, write `type="text" data-flatpickr placeholder="YYYY-MM-DD" autocomplete="off" class="form-input"` (`templates/roster/week.html` is the reference).
- **Employee list filters (q + department + team) — reuse `accounts.filters`.** For any page that lists people, apply `apply_employee_filters(qs, user, request)` to the queryset and spread `employee_filter_context(user, request)` into the template context, then drop `{% include "partials/_employee_filter_controls.html" %}` inside the page's `<form method="get">`. The scoping is security-aware (locked users clamped to their own department/teams; tampered `?team=` ignored). **The team dropdown depends on the department client-side**, not by reloading: pass an *un-narrowed* `teams` list, render `data-department="{{ t.department_id }}"` on every `<option>` and `data-team-for="<dept select id>"` on the team `<select>`, and `base.html::wireDepartmentTeamCascade` filters it on change — which is what makes it work inside a hover popover (`leave/list.html`, `roster/week.html`), where a reload would close the panel. Server-side narrowing would strand that option snapshot on one department. The user create/edit form uses the other half of the same rule (`static/js/dept-team-cascade.js` + `/employees/ajax/teams/`, `/employees/ajax/subteams/`), with `accounts.forms._OrgCascadeMixin` narrowing the querysets and rejecting a mismatched pair server-side. Custom report views that don't filter a queryset directly (e.g. shift-summary via `build_shift_summary`) pass `team_id=effective_team_id(...)` and `q=` into their filter dataclass. Roster keeps its own private helpers (extra `?employee=` logic) — don't refactor it into these.
- **Employee search — always `accounts.filters.employee_search_q(q, prefix=...)`, never a hand-rolled `icontains`.** Employee ID and email are unique, so they match **exactly** (`539` never finds `1539`; email matches the full address or the part before `@`); only first/last name is a substring match. This applies to every search box, list filter and as-you-type picker. For a model that reaches the employee through an FK, pass `prefix="employee__"` (or `"resignation__employee__"` etc.); OR any extra non-identity fields onto it (`employee_search_q(q, prefix="employee__") | Q(file_reference__icontains=q)`). `accounts/tests_search.py::SearchGuardTests` fails on any `employee_id`/`email`/`username`/`employee_code` `__icontains`/`__contains` outside tests and migrations (unified 2026-10-30 after the roster grid kept matching IDs partially).
- **Page layout — the app is a fixed shell; content scrolls inside `<main>`, not the window.** `base.html` pins the sidebar + topbar and makes `<main>` the sole vertical scroll region (`h-screen overflow-hidden` body → `<main class="flex-1 min-h-0 overflow-y-auto">`). A slim footer (`partials/footer.html`, copyright + Project Credits link) is pinned *below* `<main>`, outside the scroll region (added 2026-10-30, reversing the old "no page footer" rule — `docs/PLAN.md` "App-shell layout"); never move it inside `<main>`, or every `.page-fill` page overflows. Credits live in `core/credits.py` (plain data, no model); the page is also a "Project Credits" main menu (`award`, rank 100) in `seed_orbis`. Two page types:
  - **Simple pages** (dashboards, forms, profiles, card grids, detail/report views): do nothing — they just scroll inside `<main>`. This is the default and covers most pages.
  - **Data-table list pages** (the header must stay put while rows scroll): make the `{% block content %}` root a **`.page-fill`** (full-height flex column). Put filters/toolbars/tabs as `shrink-0` children, wrap the table in **`<div class="card p-0 table-scroll">`** with **`<table class="table-simple table-sticky">`** (add `table-sticky` to bespoke `min-w-full`/`w-full` tables too), and end with **`{% include "partials/_pagination.html" %}`** for the pinned Invelo-style pager (numbered range with ellipsis + First/Prev/Next/Last + 25/50/100 size picker; omit when the view isn't paginated). Show a top-left total via **`{% include "partials/_result_count.html" with count_noun="users" %}`** just above the table. For the size picker + `?per_page=` to work, `ListView`s add **`core.pagination.PageSizeMixin`** (and set `paginate_by = 25`); custom views that build a Python list call **`core.pagination.paginate_list(request, rows)`** and spread its keys into context (it exposes `rows`, `page_obj`, `paginator`, `is_paginated`, `page_sizes`, `current_page_size`); the export path uses the full unpaginated list. `.table-scroll` = the bounded scroll container that makes `thead th { position: sticky; top: 0 }` actually pin; a plain `overflow-x-auto` wrapper does NOT work (it becomes an unbounded scroll box). Sticky header cells must be **opaque** — don't put translucent `bg-*/NN` tints on `<th>` (rows bleed through); tint the `<td>` cells instead. For a scrolling **card-list** (not a `<table>`, e.g. `offboarding/clearance_queue.html`) add `.table-scroll` to the list container directly. The shared pagination uses the `qs_replace` tag (`dynamic_menu/templatetags/menu_extras.py`) so every active filter param survives paging.
  - **Table density — `.table-simple` cells are `px-4 py-2`. Don't re-loosen them, and measure before "tightening" anything else.** That padding was cut from `py-3` on 2026-09-06 (leave list 13 → 15 rows on screen, users 15 → 18, shift types 16 → 19, payroll runs 17 → 21); `<th>` stays `py-3` so headers still read as headers. **Bespoke `min-w-full`/`w-full` tables are a legitimate choice, not drift**, for report-shaped pages: wide numeric grids set their own tighter cells (`leave/shift_summary.html` and `payroll/report.html` use `px-2 py-1`), and converting those to `.table-simple` would make them *looser*. Every bespoke list table in the repo was already at `py-2` or below before `.table-simple` was tightened — it was the roomy outlier, they were not lagging — so a conversion buys consistency, never rows. The four worth folding in eventually are `offboarding/case_list.html`, `offboarding/manager_ack_queue.html`, `documents/my_documents.html` and `documents/all_documents.html`, which hand-roll one identical `<th>` class string between them; that's a de-duplication, and it does shift their headers (`py-2 px-3` → `px-4 py-3`), so it isn't visually free.
